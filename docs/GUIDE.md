# Руководство

## Установка

Скачай `AntiAFK.exe` из [релизов](https://github.com/BxdiS/antiafk/releases) и запусти. Всё — приложение портативное, один файл, без установщика и без прав администратора.

Важная деталь: настройки, лог и прогресс цикла живут только в памяти процесса. При каждом запуске всё с нуля, на диск ничего не пишется. Единственное исключение — пара временных файлов на несколько секунд в момент применения обновления.

## Трей

| Пункт | Что делает |
|-------|------------|
| Запустить / Остановить | Старт и пауза. Состояние цикла держится до перезапуска приложения |
| Обновить | Появляется, когда обновление уже скачано. Приложение заменяет само себя и перезапускается |
| Настройки | Язык (RU/EN) и путь к лаунчеру. Действуют до закрытия |
| Открыть лог | Журнал текущей сессии — окно в памяти, не файл на диске |
| Выход | Закрыть полностью |

### Обновления

Проверка происходит при запуске и потом раз в несколько часов (по умолчанию каждые 6, настраивается в конфиге). Берётся последний опубликованный релиз с GitHub — draft и pre-release игнорируются.

Скачивание идёт в фоне, иконка в трее становится синей. По нажатию «Обновить» exe перезаписывает себя новой версией и перезапускается; временные файлы подчищаются сразу после.

Перед этим скачанный файл сверяется с `AntiAFK.exe.sha256` из того же релиза. Если чек-сумма не сошлась или файла с ней в релизе нет, обновление отбрасывается: приложение заменяет само себя и сразу запускает результат, поэтому «не смогли проверить» здесь не считается за «проверено».

## Выбор точки спавна

После подтверждения персонажа игра показывает карту с полосой круглых иконок внизу — это точки возрождения. Набор у каждого свой, полоса выровнена по центру, поэтому появление ещё одной иконки сдвигает все остальные: «третья слева» у двух игроков означает разные места.

Поэтому бот не жмёт позицию, а смотрит, что нарисовано на иконках. Как это работает:

1. Снимается полоса внизу экрана и подбирается количество иконок — то, при котором все места заняты, а сразу за краями пусто.
2. Каждая иконка сравнивается с эталонами, зашитыми в приложение.
3. Кликается первая иконка из списка `spawn.priority`, которая реально есть у игрока.

Что приложение умеет узнавать:

| id | Что это | Иконка |
|----|---------|--------|
| `exit_point` | Место выхода | карта с меткой |
| `starting_spawn` | Начальный спавн | самолёт |
| `personal_house` | Личный дом | дом с крышей |
| `personal_apartment` | Личная квартира | высотка |
| `family_house` | Семейный дом | двое людей |
| `family_mansion` | Семейный особняк | двое людей — та же самая иконка |
| `family_office` | Семейный офис | офисное здание |

Порядок по умолчанию: `personal_house` → `personal_apartment` → `family_house` → `family_office` → `family_mansion` → `exit_point` → `starting_spawn`.

**Про дом и особняк.** Игра рисует их одной и той же иконкой — не похожей, а буквально той же: маски отличаются на 3 пикселя из 1936, и это сглаживание от смещения на полпикселя. Никакое распознавание по картинке их не различит.

Различаются они счётом. Особняк не бывает без дома, а в полосе он идёт перед ним, поэтому одна «людская» иконка — это всегда дом, а две — особняк и следом дом. Именно поэтому названия у общего глифа выравниваются по концу списка, а не по началу.

Если ни одной из списка нет — жмётся крайняя левая иконка. Если полосу вообще не удалось прочитать — клик в старую фиксированную точку `(1053, 964)`, как было раньше.

В логе видно всё, что бот увидел:

```
Auto-login: spawn bar has 5 icon(s) on row y=964 (fit 1.00): [1] exit_point (pin 0.20) @768  [2] starting_spawn (airplane 0.03) @864  [3] family_house (people 0.00) @960  [4] family_mansion (people 0.02) @1056  [5] family_office (office 0.03) @1152
Auto-login: selecting spawn point "exit_point" at (768, 964), icon 1 of 5.
```

Иконка, для которой в приложении нет эталона, попадает в лог как `unknown` вместе с её подписью и картинкой глифа — по ним эталон добавляется одной строкой в `SpawnIconCatalog`. Заготовку строки печатает инструмент:

```bash
dotnet run --project tools/GenerateSpawnIcons -- screenshot.png
```

Пороги совпадения выставлены по замерам, а не на глаз. Проверка делалась так: каждая из четырнадцати иконок опознавалась каталогом, из которого её собственный эталон убран. Все четырнадцать опознались верно — худшее расстояние до своего глифа 0.22, ближайший чужой 0.36, порог 0.30 стоит между ними. Поэтому на иконку, которой нет в каталоге, ответ будет `unknown`, а не «ближайшее здание»: не узнать — потерять одну точку спавна, узнать неправильно — заспавнить игрока не там, где он просил.

## Конфигурация

Настройки задаются через трей → **Настройки** и не сохраняются на диск. Структуру полей можно посмотреть в [config.example.json](config.example.json) — это справка, а не файл, который приложение читает.

`launcherPath` пустой означает автопоиск лаунчера в стандартных путях Windows. Координаты интерфейса и тайминги зашиты в код, через конфиг их не поменять. Это же касается и `spawn.priority`: поле есть, но задать его пока можно только значением по умолчанию в коде — файл конфигурации в планах ([ROADMAP](../ROADMAP.md), v1.5.0).

## Сборка из исходников

```bash
git clone https://github.com/BxdiS/antiafk.git
cd antiafk
dotnet build src/AntiAfk.App/AntiAfk.App.csproj
dotnet run --project src/AntiAfk.App/AntiAfk.App.csproj
```

Как разложен код:

```
src/
  AntiAfk.Core/           — движок, координаты, состояние
  AntiAfk.Infrastructure/ — WinAPI, работа с экраном, конфиг и лог (оба в памяти)
  AntiAfk.App/            — трей, окно настроек (WinForms), обновления
```

## Релизы

CI срабатывает на push тега `v*`:

```bash
git push origin main
git tag v1.0.1
git push origin v1.0.1
```

Дальше GitHub Actions собирает самодостаточный однофайловый `.exe` под win-x64 (рантайм .NET внутри, ставить рядом ничего не нужно), считает SHA-256 и публикует релиз сразу — не черновиком, с автогенерированными release notes.

Публикация автоматическая намеренно. В прежней схеме на Velopack релиз оставался draft, и про ручное нажатие Publish легко было забыть — именно из-за этого автообновление «не работало».

В релиз попадают два файла:

| Файл | Зачем |
|------|-------|
| `AntiAFK.exe` | То, что скачивают пользователи |
| `AntiAFK.exe.sha256` | Чек-сумма, если кто-то хочет проверить целостность |

Автогенерация release notes даёт просто список коммитов. Если хочется по-человечески — отредактируй описание релиза после публикации.

## Подпись кода

`AntiAFK.exe` не подписан, поэтому SmartScreen ругается на первый запуск. Это нормально для любого малоизвестного бинарника и никак не связано с тем, как он собран.

План — получить бесплатную подпись от [SignPath](https://signpath.org/). Проект под [GPL-3.0](../LICENSE), а OSI-совместимая лицензия — их основное требование (проприетарные и non-OSI они не подписывают). После одобрения в CI добавляется шаг после `dotnet publish`, который подписывает `publish/AntiAFK.exe` напрямую — без `vpk --signTemplate`, это осталось от старой Velopack-схемы.

## Если что-то не работает

| Симптом | Куда смотреть |
|---------|---------------|
| Игра не находится | Нужен процесс `GTA5.exe` либо окно клиента Majestic RP с версией в заголовке |
| Клики уходят мимо | В начале лога есть строки `Display ...` с масштабом каждого монитора. Всё, что не 100%, сдвигает координаты — игра должна быть на мониторе со 100% |
| Спавн не там, где ожидался | Строка `spawn bar has N icon(s)` в логе показывает, что бот увидел и чем счёл каждую иконку. `unknown` означает, что эталона для неё нет — рядом лежат подпись и глиф, чтобы его добавить |
| Движок остановился сам | После пяти падений подряд он перестаёт перезапускаться, чтобы не крутить один и тот же сбой по кругу. Причина — в консоли логов, «Запустить» пробует заново |
| Обновления не приходят | Последний релиз должен быть опубликован (не draft, не pre-release) и содержать `AntiAFK.exe`. Если рядом нет `AntiAFK.exe.sha256`, обновление отбрасывается как непроверяемое |
| Workflow не запустился | Тег обязан начинаться с `v` |
| Настройки сбросились после перезапуска | Так и задумано — портативная версия ничего не хранит между запусками |
